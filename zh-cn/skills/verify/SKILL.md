# 验证

执行用户请求的交付后验收验证。

验证回答：

> 已交付的行为是否满足已批准的验收契约？

这不是代码审查，也不会修改交付内容。

## 规则

### 1. 验证契约

使用相关的权威产物：

- 需求
- 验收标准
- 已批准的产品行为
- 适用的技术设计或架构约束
- 兼容性要求

实现是验证的主体，而不是预期行为的来源。

### 2. 验证可观察行为

使用能够展示所需行为的最高稳定接缝，例如：

- 用户可见的行为
- 公共 API 或 CLI
- 协议或集成边界
- 服务或领域边界

仅在必要时使用较低层级的检查。

### 3. 测试是证据，而非权威

当现有测试确实能够展示验收标准时，可以复用它们。

仅凭测试通过、CI 或代码审查并不能证明验收通过。

### 4. 验证期间不进行修复

不得修改：

- 产品代码
- 测试
- 需求
- 规格
- 技术设计

不得为了获得通过而弱化或重新解释验收预期。

### 5. 不得臆造预期行为

如果权威产物允许存在实质性不同的解释，则将受影响的标准标记为 `BLOCKED`。

报告模糊性，而不是选择一种解释。

## 流程

### 步骤 1 — 确立验收契约

识别相关的：

- 需求
- 验收标准
- 可观察的约束
- 兼容性预期

不得将范围扩大到已批准契约之外。

### 步骤 2 — 选择验证证据

对于每条验收标准，确定能够展示它的最高稳定接缝和最小充分检查。

适当时复用现有测试或接口。

### 步骤 3 — 执行验证

在实际可行的情况下，实际运行已交付的行为。

对于每条所需标准，记录：

- `PASS` — 证据展示了所需行为
- `FAIL` — 观察到的行为与所需行为相矛盾
- `BLOCKED` — 当前无法可靠地验证通过或失败

不得仅因未观察到失败就推断为 `PASS`。

### 步骤 4 — 诊断失败

不得假定失败的标准就是实现缺陷。

当原因尚未确定时，使用 [DIAGNOSE.md](./DIAGNOSE.md) 来识别：

- 根本原因
- 分类
- 支持证据
- 受影响的权威或产物
- 所需的修正
- 所需的回归验证

诊断描述必须改变什么；它不选择或调用修正工作流。

### 步骤 5 — 检查相关回归

当已交付的变更可能影响已建立的相邻行为时，运行回归检查。

保持范围与变更及其风险相称。

### 步骤 6 — 报告

生成一份简洁的验证报告。

## 输出

# 验证：<标题>

## 结果

PASS | FAIL | BLOCKED

## 验收结果

### <标准>

**结果：** PASS | FAIL | BLOCKED

**证据：** <可观察的证据>

对每条所需标准重复。

## 失败

对于每个失败，在适用时：

- 预期行为
- 观察到的行为
- 根本原因和分类
- 所需的修正

无失败时省略。

## 阻塞项

描述任何妨碍可靠验证的因素。

不存在时省略。

## 回归检查

相关的回归检查及结果。

不必要时省略。

## 总体结果

- 仅当每条所需标准都通过时为 `PASS`
- 当任何所需标准失败时为 `FAIL`
- 当没有失败但一条或多条所需标准无法可靠验证时为 `BLOCKED`

当每条所需标准都有充分证据或明确的阻塞项时，验证即告完成。
