# 失败诊断

当验收验证失败且根本原因尚未确定时，使用此协议。

目标是：

> 哪里出了问题，源自何处，必须改变什么？

不要假设实现是错误的。

## 流程

1. 确定观察到的行为和预期行为。
2. 收集最强的可用复现证据。
3. 检查相关的权威链：
   - 产品需求
   - 已接受的技术设计
   - 架构决策
   - 规格和验收标准
   - 测试
   - 实现
   - 运行时环境和外部依赖
4. 区分症状、直接原因和根本原因。
5. 识别最早出错或模糊的权威层级。
6. 对失败进行分类并描述所需的修正。

如果仓库证据能够回答事实性问题，则检查它而不是询问用户。

如果确实存在属于用户所有的模糊性，则报告其需要决策，而非自行发明一个。

## 分类

使用一个主要分类：

- **实现缺陷** — 实现违反了明确的既定契约 → 通过授权的实现路径修正实现
- **测试缺陷** — 测试断言了既定契约未要求的行为 → 通过授权的实现路径修正测试
- **规格缺陷** — 实现契约是错误的、不完整的、矛盾的或模糊的 → 修订规格和受影响的验收标准
- **设计缺陷** — 已接受的技术设计不满足既定的意图或约束 → 在修正下游产物或实现之前修订技术设计
- **架构决策缺陷** — 一个持久的架构决策不再有效 → 确立替代决策并保留架构决策历史
- **产品需求缺陷** — 既定的产品行为或范围未反映实际的产品意图 → 在修正下游产物之前修订产品需求
- **环境/依赖问题** — 既定契约是合理的，但运行时环境或外部依赖阻止了所需行为 → 修正或恢复受影响的环境或依赖
- **未解决** — 证据不足以识别最早出错层级 → 在授权修正之前收集更多证据

## 根本原因规则

优先选择最早出错的权威层级。

不要围绕不正确的上游契约修补下游行为。

不要将测试视为自动具有权威性。

不要重写历史架构决策来隐藏已更改的决策。

## 结果

将诊断结果返回给 `verify`，包括：

- 根本原因
- 分类
- 支持证据
- 受影响的权威或产物
- 所需的修正
- 修正后所需的回归验证
