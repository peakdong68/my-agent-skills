# 编写 PRD

将早期产品想法转化为清晰、有边界且已批准的产品方向。

PRD 回答：

> 我们应该构建什么，为什么重要，以及它应该产生什么结果？

典型流程：

想法 / 愿景 → PRD → RFC → 规范 → 规划 / 实现

## 规则

### 1. 发现产品意图，而非技术设计

此技能负责：

- 问题和机会
- 用户或受益者
- 期望结果和价值
- 产品行为
- 范围和非目标
- 产品约束
- 产品级成功

不要做出新的架构或实现决策。

技术设计属于 RFC。

### 2. 先检查证据，再询问

在询问用户问题之前，检查相关可用证据：

- 代码和测试
- 当前行为
- 文档
- 配置
- 现有 PRD、RFC、ADR 和规范
- 研究和原型
- 问题或任务历史记录
- 既定领域术语

不要要求用户确认可用证据已能确定的事实。

代码库证据定义当前行为和约束，而非未来产品意图。

### 3. 一次问一个产品问题

当仍有阻塞性用户决策时，恰好问一个最高价值的问题。

问题应明确：

- 需要什么决策
- 为何重要
- 你的建议
- 相关时的主要权衡

不要运行固定问卷。

### 4. 区分问题与提议的解决方案

用户可能从技术解决方案开始。

将其保留为输入，但首先确立：

- 底层问题
- 期望结果
- 提议的机制是否实际上是产品约束

不要默默将建议的实现转化为产品需求。

未解决的技术提案属于 RFC。

### 5. 保持范围最小且明确

将有意义的范围分类为：

- **核心** — 预期价值所必需的
- **辅助** — 有用但非必需
- **推迟** — 有意推迟
- **非目标** — 明确在此工作之外

优先选择能够传递预期结果的最小连贯核心。

### 6. 不猜测未解决的决策

区分：

- 可从证据回答的事实
- 由用户拥有的产品决策
- 由 RFC 拥有的技术问题
- 有意推迟的工作

如果产品意图仍然模糊，则询问。

如果技术问题不阻塞产品定义，则推迟到 RFC。

在此技能激活期间不要编辑产品代码。

## 流程

### 第 1 步 — 捕获方向

使用已确立的内容创建或更新 `docs/prd/<date>+<feature>.md`：

- 愿景
- 问题或机会
- 用户或受益者
- 期望结果
- 已知范围
- 已知约束

不要通过编造来填补空白。

### 第 2 步 — 检查证据

探索相关项目证据以确立：

- 当前行为
- 现有能力
- 先前决策
- 领域术语
- 相关约束

仅在发现对产品意图、范围、行为或约束有实质影响时，才记录发现。

需要设计决策的技术发现属于 RFC。

### 第 3 步 — 解决产品决策

识别对以下方面有实质影响的未解决决策：

- 结果
- 行为
- 范围
- 用户体验
- 兼容性
- 优先级
- 风险
- 成功

如果仍有一个或多个未解决，则问单个最高价值的问题并停止。

在每次回答后：

1. 更新 PRD
2. 检查新相关的证据
3. 重新计算未解决决策
4. 必要时重复

不要进入技术设计或实现。

### 第 4 步 — 塑形产品

完善：

- 核心范围
- 辅助范围
- 推迟工作
- 非目标
- 产品约束
- 预期产品行为
- 产品级成功

移除预期价值不要求的复杂性。

### 第 5 步 — 收敛

当满足以下条件时，PRD 即可进行最终审查：

- 问题和期望结果清晰
- 用户或受益者清晰
- 产品价值已理解
- 预期产品行为足够清晰
- 核心范围有边界
- 有意义的非目标明确
- 重要产品约束已知
- 产品级成功已定义
- 不存在阻塞性产品决策
- 剩余技术问题可以移至 RFC，而无需 RFC 猜测产品意图

技术架构不需要解决。

在最终审查之前，将 PRD 重写为最终形式。

移除：

- 已解决的问题
- 重复事实
- 已放弃的想法
- 探索性推理

保留：

- 决策
- 范围
- 约束
- 相关证据
- 重要假设
- 与下游工作相关的技术问题

### 第 6 步 — 最终审查

提供简洁的摘要，包含：

- 愿景和问题
- 期望结果和价值
- 核心范围
- 相关时的辅助或推迟范围
- 非目标
- 重要约束
- 产品级成功
- 推迟到下游的技术问题
- 产物状态

然后停止。

不要在同一个回合中开始 RFC 设计或实现。

在 PRD 获得批准之前，需要用户明确批准最新的最终审查。

如果之后产品方向发生重大变更，则重复最终审查。

## PRD 模板

在可用时使用项目现有的 PRD 格式。

否则使用：

# PRD：<标题>

## 状态

草稿 | 提议 | 已批准

## 愿景

此产品或功能应实现什么？

## 问题

我们在解决什么问题或机会，以及为何重要？

## 用户

谁受益或受影响？

仅包含与实际产品决策相关的群体。

## 期望结果

当此成功时，什么应变得可能？

## 产品行为

描述重要的用户可见或外部可观察行为。

关注结果而非实现机制。

## 范围

### 核心

传递预期价值所需的能力。

### 辅助

有用但非核心所必需的相关能力。

### 推迟

有意推迟的能力。

## 非目标

明确在此工作之外的相邻问题或能力。

## 约束

影响产品行为的既定产品、平台、兼容性、业务、政策或运维约束。

## 成功

表明预期价值已实现的可观察产品级结果。

当不需要指标时，不要制造指标。

## 风险与假设

仅包含影响范围、价值或预期行为的重要产品假设或风险。

## 未解决的技术问题

有意推迟到下游设计的技术问题。

当没有剩余时省略。

## 参考文献

相关研究、问题、PRD、RFC、ADR、规范、原型或代码库证据。

## 交接

当下游工作不需要猜测产品意图时，已批准的 PRD 即可用于 RFC 或规范。

将 PRD 用作权威产品方向。

PRD 定义**是什么和为什么**。

RFC（在需要时）决定**如何做**。
