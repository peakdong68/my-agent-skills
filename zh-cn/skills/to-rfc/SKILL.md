# 编写 RFC

当重大设计决策仍未解决时，在实现之前产出已批准的技术设计。

RFC 回答：

> 应如何设计和实现此变更，以及为什么？

它不是 PRD、规范、任务列表、路线图或实现。

当产品意图已充分确立时，RFC 不需要 PRD。

## 规则

### 1. 不要实现

在最新 RFC 获得明确批准之前，保持在设计模式。

在 RFC 工作期间不要编辑产品代码。

之前的“实现”、“继续”或“继续推进”并不代表对后续 RFC 修订版本的批准。

### 2. 确立产品意图

在做出设计决策之前，确立相关的：

- 问题
- 期望结果
- 预期行为
- 范围
- 产品约束

在有可用 PRD 时使用已批准的 PRD。

产品意图也可来自明确的对话或其他权威项目证据。

如果 RFC 工作需要猜测未解决的产品意图，则停止并建议通过 `to-prd` 解决它。

### 3. 先检查，再询问

如果项目证据能回答问题，则检查它，而不是询问用户。

检查相关：

- 代码和测试
- 配置
- 文档
- PRD
- 规范
- ADR
- 相关 RFC
- 研究
- 原型
- 问题或任务历史记录

代码库证据确立当前行为和约束，而非未解决的用户意图。

### 4. 仅询问真正的决策

仅当重大决策无法从既定意图、证据或技术验证中解决时，才询问用户。

典型的用户决策包括：

- 产品行为
- 范围
- 用户体验
- 兼容性
- 安全或风险承受能力
- 迁移预期
- 运维预期
- 有意权衡

一次恰好问一个最高价值的问题。

包含：

- 该决策
- 为何重要
- 你的建议
- 主要权衡

不要问流程性问题。

### 5. 优先最小充分设计

每个有意义的机制都必须由需求、约束、兼容性需求、安全需求、运维需求或已证明的技术必要性来证明其合理性。

如果移除某物不会破坏任何重要内容，则移除它。

避免推测性可扩展性。

## 流程

### 第 1 步 — 定义问题

在不预设解决方案的情况下重述问题。

确定：

- 当前行为
- 期望结果
- 受影响的用户或系统
- 为何当前行为不足
- 既定产品约束

在没有冲突证据的情况下，不要重新开启既定的产品决策。

### 第 2 步 — 检查当前系统

理解相关的：

- 架构和边界
- 数据/控制流
- 契约
- 状态归属
- 失败行为
- 生命周期/并发
- 兼容性约束
- 测试接缝

使用现有项目术语。

当设计实质性地引入或变更领域概念、所有权、不变量、关系或边界时，使用 `domain-modeling`。

### 第 3 步 — 构建决策清单

将未解决的问题分类为：

- **代码库** — 从项目证据中回答
- **研究** — 从权威技术证据中回答
- **用户** — 需要意图、范围、兼容性、用户体验或风险选择
- **实验** — 需要基准测试、原型、兼容性测试或概念验证

不要将未知项转化为假设。

### 第 4 步 — 评估备选方案

仅考虑有意义的备选方案。

对每个相关备选方案记录：

- 方法
- 优点
- 成本
- 为何选择或拒绝

不要仅仅为了填充 RFC 而编造备选方案。

### 第 5 步 — 解决技术未知项

如果某个技术假设对设计有实质性影响且无法自信回答，则获取最小充分证据。

这可能包括：

- 针对性研究
- 基准测试
- 兼容性测试
- 原型
- 概念验证

阻塞性技术未知项必须在 RFC 接受之前解决。

### 第 6 步 — 收敛

当满足以下条件时，RFC 即可进行最终审查：

- 问题和期望结果清晰
- 目标和非目标清晰
- 相关代码库证据已被检查
- 所需用户决策已解决
- 主要边界清晰
- 重要流程和契约清晰
- 失败行为已理解
- 在相关时，兼容性和迁移已处理
- 有意义的备选方案已被考虑
- 权衡和风险明确
- 阻塞性技术未知项已解决
- 不存在阻塞性未决问题

如果仍存在未解决的产品决策，则停止，而非在 RFC 内部做出决策。

## 第一性原理检查

当设计显得复杂时，问：

1. 实际问题是什么？
2. 哪些事实是绝对确定的？
3. 哪些部分是假设或惯例？
4. 每个主要机制对应哪个需求？
5. 如果移除该机制，什么会被破坏？
6. 满足所有既定约束的最小设计是什么？

## RFC 模板

如果代码库有现有 RFC 格式，则使用该格式。

否则使用：

# RFC：<标题>

## 状态

草稿 | 提议 | 已接受 | 已拒绝 | 已取代

## 摘要

问题、提议的设计以及为何优先选择它。

## 动机

当前限制及其重要性。

## 目标

设计必须完成什么。

## 非目标

设计有意不处理什么。

## 当前状态

相关的现有行为和架构。

## 约束

相关的产品、架构、兼容性、安全、平台或运维约束。

## 提议设计

描述推荐的设计。

仅涵盖相关主题，例如：

- 架构和责任边界
- 数据/控制流
- 接口和契约
- 状态和生命周期
- 失败处理
- 并发
- 安全
- 兼容性和迁移
- 运维

## 考虑的备选方案

有意义的备选方案及拒绝原因。

## 决策理由

为何此设计最能满足目标和约束。

## 权衡

有意接受的重要成本。

## 风险

有意义的风险及缓解措施。

## 验证

支持重要假设的证据、研究、基准测试、原型或概念验证结果。

## 延期工作

明确推迟且不阻塞此设计的工作。

## 未决问题

仅包含未解决的问题。

若无，则省略。

## 参考文献

相关的 PRD、ADR、RFC、规范、研究、问题、原型、代码库证据或权威技术来源。

## 最终审查

当设计已收敛：

1. 将状态设置为 `Proposed`。
2. 提供简洁的摘要，包含：
   - 问题
   - 目标和非目标
   - 提议设计
   - 关键决策
   - 被拒绝的备选方案
   - 权衡
   - 风险
   - 验证和延期工作
3. 停止。
4. 等待用户明确批准。

获得明确批准后，将状态设置为 `Accepted`。

重大的设计变更需要再次进行最终审查。

## 编写规则

- 解释为什么，而不仅仅是什么。
- 区分事实、约束、决策和假设。
- 优先使用稳定的设计概念，而非私有实现细节。
- 不要编写对话记录。
- 从最终 RFC 中移除已解决的问题。
- 不要制造复杂性、备选方案或问题。
- 使用项目术语。
- 保持可复用示例的领域中立。

## 产物

在 `docs/rfc` 下创建或更新 RFC。

在可用时使用项目现有的命名约定。否则使用：

`docs/rfc/<date>+<feature>.md`

RFC 是该变更的权威技术设计产物。

在设计期间：

- `草稿` — 设计仍在开发中
- `提议` — 设计已收敛，可供用户审查
- `已接受` — 最新的提议设计已获得明确批准
- `已拒绝` — 提案已被拒绝
- `已取代` — 已被后续设计取代

## 交接

当满足以下条件时，已接受的 RFC 即可用于下游规范：

- 技术设计已充分解决
- 主要契约和边界已确立
- 阻塞性技术未知项已解决
- 下游工作不需要自行发明设计决策

RFC 是权威技术设计。

下游规范将该设计转化为实现和验收需求。
