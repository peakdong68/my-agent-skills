# 诊断

在更改任何内容之前，调查用户报告的交付后差异。

目标是：

> 哪里出了问题，源自何处，以及哪个层应该改变？

不要假设代码有误。
在诊断期间不要修改产品代码。

## 流程

1. 确立观察到的行为和用户的预期行为。
2. 在可行时复现或收集最强可用证据。
3. 检查相关的权威链：
   - PRD / 产品意图
   - 已接受的 RFC
   - ADR
   - 规范 / 验收标准
   - 测试
   - 实现
   - 运行时环境或外部依赖
4. 区分症状、直接原因和根本原因。
5. 识别实际有误或模糊的最早权威层。
6. 确定影响和适当的修正路径。

如果代码库证据能回答事实性问题，则检查它，而不是询问用户。
如果剩余的模糊性确实属于用户决策，则一次问一个最高价值的问题。

## 分类

使用一个主要分类：

- **实现错误** — 实现违反了清晰的既定契约 → `/fix-bug`
- **测试缺陷** — 测试断言了既定契约不要求的行为 → 通过授权的实现路径修正测试
- **规范缺陷** — 规范有误、不完整、矛盾或模糊 → 通过 `/to-spec` 修订
- **设计缺陷** — 已接受的设计未达成既定意图或约束 → 重新开启 `/to-rfc`
- **架构决策缺陷** — 持久的架构决策必须变更 → `/to-rfc`，然后在适当时 `/adr`
- **产品需求缺陷** — 实现的行为与设计/规范匹配，但不符合实际产品意图 → 重新开启 `/to-prd`
- **环境/依赖问题** — 实现契约正确，但执行环境或依赖导致失败
- **未解决** — 证据不足以安全分类

## 根本原因规则

优先选择最早错误层。

不要围绕有误的上游契约修补下游代码。
不要将测试视为自动具有权威性。
不要重写历史 ADR 来隐藏已变更的决策。

## 产物

在可用时使用项目现有的缺陷、事件、调查或问题格式。

对于简单问题，单独的持久诊断记录是可选的，但当问题出现以下情况时，应创建：
- 更改或揭示规范中的模糊性
- 重新开启 RFC 或 ADR
- 更改产品需求
- 跨越多个层
- 具有迁移或兼容性影响
- 可能再次发生或需要未来解释

## 输出

# 诊断：<标题>

## 观察结果

实际发生了什么。

## 预期行为

应该发生什么，以及哪个权威证据确立了它。

## 证据

与诊断相关的复现、日志、测试或代码库事实。

## 根本原因

最早识别的原因。

## 分类

来自上述列表的一个分类。

## 影响

受影响的行为、产物、兼容性、数据或环境。

## 推荐的修正方案

哪个层应该改变，以及下一个适当的技能/行动。

## 回归验证

修正后的行为应如何验证。

## 状态

已诊断 | 需要决策 | 需要调查
