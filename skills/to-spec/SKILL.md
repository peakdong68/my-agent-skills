# 转写为规范

将既定的需求、设计决策和代码库证据转化为可实现规范。

规范回答：

> 到底必须实现什么，以及我们如何知道它是正确的？

它是实现与验收验证共享的契约。

典型流程：

PRD → RFC → 规范 → 工单 → 实现 → 验证

## 规则

### 1. 综合，而非重新设计

使用相关方面已确立的决策：

- 对话上下文
- PRD
- RFC
- ADR
- 现有规范
- 原型
- 代码库证据
- 问题或任务历史记录

不要重新开启已解决的决策。

不要仅仅为了完成规范而引入新的产品、架构、用户体验、兼容性、安全、迁移或风险决策。

如果实现需要新的决策，则规范尚未准备就绪。

### 2. 不进行访谈

不要向用户提出澄清性问题。

通过检查可用证据来解决代码库可回答的事实。

如果所需的产品或设计决策缺失、矛盾或模糊：

- 将其记录为阻塞项
- 识别拥有该问题的上游决策
- 不要猜测

带有阻塞性未知项的规范不具备实施就绪性。

### 3. 检查代码库证据

在最终定稿前，检查相关代码库，除非已被充分探索。

仅检查相关的内容，例如：

- 当前代码和行为
- 测试和固件
- 配置
- 文档
- 架构边界
- 现有契约
- 相关的 PRD、RFC、ADR 和规范
- 既定的测试模式

使用项目术语，并尊重现有的权威决策。

代码库证据确立当前行为和技术约束。它不得默默重新定义既定的产品意图。

### 4. 指定行为，而非编码步骤

描述：

- 可观察行为
- 契约
- 不变量
- 约束
- 相关失败行为

优先：

> 成功保存的偏好必须在受支持的会话间保持有效。

而非：

> 向设置表添加一个布尔列。

仅当实现细节本身是既定契约或已接受设计决策的一部分时，才包含它们。

不要将规范变成实现计划。

### 5. 使需求具有规范性和可验证性

使用稳定的需求 ID：

- `R-001`
- `R-002`

在适当时使用规范性语言：

- **必须**
- **禁止**
- **应当**
- **不应当**
- **可以**

每个**必须**和**禁止**必须具有可观察的验证路径。

在可行情况下，需求应保持原子性，并精确到实现不需要自行发明行为。

### 6. 优先使用最高的稳定验证接缝

通过能够可靠展示需求的最高稳定现有边界来验证行为。

优先：

外部/公共行为
→ 集成/领域/服务边界
→ 模块边界
→ 内部组件

优先使用现有接缝，而非引入仅用于测试的接缝。

当所需行为可以通过更高边界展示时，不要测试私有实现细节。

目标不是最大化接缝数量。使用提供足够行为覆盖的最少数量的稳定接缝。

## 流程

### 第 1 步 — 确立范围和证据

提取已确立的：

- 目标
- 所需行为
- 范围
- 排除项
- 约束
- 兼容性预期
- 相关产品和设计决策

检查理解当前系统和现有验证模式所需的代码库证据。

不要凭空捏造缺失的决策。

### 第 2 步 — 定义需求和契约

将既定行为转化为规范性需求。

在必要时定义相关契约，例如：

- API
- 命令
- 事件
- 模式
- 状态转换
- 持久化行为
- 兼容性行为

仅包含对实现或验证有实质影响的契约。

不要仅仅为了使规范更详细而发明抽象。

### 第 3 步 — 定义验收标准

使用稳定的验收 ID：

- `AC-001`
- `AC-002`

验收标准描述可观察结果。

优先：

> 给定 `<初始条件>`，当 `<动作>`，则 `<可观察结果>`。

将验收标准映射到需求：

`R-001 → AC-001, AC-002`

每个所需行为必须可客观验证。

验收标准定义在交付后验证期间必须展示的内容；它们不应规定不必要的实现细节。

### 第 4 步 — 定义验证策略

对每个所需行为，确定如何展示它。

确定：

- 主要验证接缝
- 所需的自动化覆盖
- 可复用的现有测试模式
- 必要时进行集成、端到端或手动验证

现有测试是有用的证据，但规范应独立于当前实现定义所需行为。

优先面向行为的验证，而非面向实现的测试。

### 第 5 步 — 检查就绪性

仅当满足以下条件时，规范才准备就绪：

- 目标和范围清晰
- 所需行为明确
- 相关契约已定义
- 相关错误和边缘情况已定义
- 验收标准可观察
- 每个必须和禁止都有验证路径
- 存在可行的验证接缝
- 相关代码库证据已被检查
- 适用的 PRD、RFC、ADR 和现有规范决策得到尊重
- 在需要时，兼容性或迁移行为已定义
- 不存在阻塞性产品或设计决策
- 实现可以在不自行发明行为的情况下推进

如果任何阻塞条件失败：

- 将规范标记为 `未准备实施`
- 识别阻塞项及其所属的上游层
- 不要猜测
- 不要将其发布为准备实施

## 规范模板

如果代码库有规范格式，则使用该格式。

否则使用：

# 规范：<标题>

## 状态

草稿 | 就绪

## 目标

此实现必须达成什么结果？

## 上下文

仅包含理解和实现此规范所必需的当前行为、约束和上游决策。

## 范围

### 范围内

- ...

### 范围外

- ...

## 需求

### R-001 — <需求>

系统**必须** ...

### R-002 — <需求>

系统**禁止** ...

## 接口和契约

仅在相关时包含。

描述对实现或验证有实质约束的所需外部或内部契约。

## 错误和边缘情况

仅包含对所需行为有实质影响的情况。

## 验收标准

### AC-001 → R-001

给定 ...，当 ...，则 ...

### AC-002 → R-002

给定 ...，当 ...，则 ...

## 验证策略

### 主要接缝

可通过其展示所需行为的最高稳定边界。

### 所需覆盖

描述所需的行为验证以及应复用的相关现有测试模式。

## 兼容性和迁移

仅在相关时包含。

## 风险和延期工作

仅包含实现者需要了解的非阻塞限制、风险或明确推迟的工作。

阻塞性决策属于就绪状态部分。

## 参考文献

相关的 PRD、RFC、ADR、规范、原型、问题或代码库证据。

## 就绪状态

`准备实施`

或：

`未准备实施`

如果未就绪，列出每个阻塞项以及拥有未解决决策的上游层。

## 发布

如果规范已就绪且项目问题跟踪器已配置：

1. 发布规范
2. 应用项目的实施就绪分类标签，如 `ready-for-agent`
3. 遵循现有项目约定，不发明额外的分类

如果所需跟踪器配置不可用，则生成规范并报告无法完成发布。

如果此环境特别使用 `/setup-matt-pocock-skills` 进行跟踪器设置，则在缺少所需配置时指示用户运行它。

不要凭空捏造跟踪器配置、项目标识符、问题类型或标签。

## 编写规则

- 保持简洁、规范性和可测试性。
- 在机制之前指定结果。
- 避免使用模糊术语，如“适当”、“快速”或“优雅”，除非其含义已定义。
- 不要制造需求、边缘情况、契约或抽象。
- 不要重新开启已接受的产品或设计决策。
- 除非文件路径或代码片段本身就是既定契约的一部分，否则不要包含它们。
- 不要编写对话记录。
- 移除已解决的问题和探索性推理。
- 使用既定的项目术语。
- 仅当可选部分对实现或验证有实质影响时，才包含它们。

规范是实现和验收契约。

`implement` 使用它来确定必须构建什么。

`verify` 使用它来确定必须展示什么。

下游工单将契约分解为可执行的工作，而不重新定义它。
