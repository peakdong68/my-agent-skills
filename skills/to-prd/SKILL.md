# 编写 PRD

将早期产品想法转化为清晰、有边界且已批准的产品方向。

PRD 回答：

> 我们应该构建什么，为什么重要，以及它应该产生什么结果？

对于复杂工作，同时在规划期间将发现的技术上下文捕获到 `design.md` 中，供下游 RFC 工作使用。

典型流程：

想法 / 愿景 → PRD → RFC → 规范 → 工单 → 实现

## 规则

### 1. 发现产品意图，而非技术设计

此技能负责：

- 问题和机会
- 用户或受益者
- 期望结果和价值
- 产品行为
- 范围和非目标
- 产品约束
- 产品级成功

不要做出新的架构或实现决策。

技术决策属于 RFC。

### 2. 先检查证据，再询问

在询问用户问题之前，检查相关可用证据：

- 代码和测试
- 当前行为
- 文档
- 配置
- 现有 PRD、RFC、ADR 和规范
- 原型
- 问题或任务历史记录
- 既定领域术语

不要要求用户确认可用证据已能确定的事实。

代码库证据定义当前行为和约束，而非未来产品意图。

### 3. 一次问一个产品问题

当仍有阻塞性用户决策时，恰好问一个最高价值的问题。

问题应明确：

- 需要什么决策
- 为何重要
- 你的建议
- 相关时的主要权衡

不要运行固定问卷。

不要问可从项目证据中找到答案的问题。

### 4. 区分问题与提议的解决方案

用户可能从技术解决方案开始。

将其保留为输入，但首先确立：

- 底层问题
- 期望结果
- 提议的机制是否实际上是产品约束

不要默默将建议的实现转化为产品需求。

未解决的技术提案属于 RFC。

### 5. 保持范围最小且明确

将有意义的范围分类为：

- **核心** — 预期价值所必需的
- **辅助** — 有用但非必需
- **推迟** — 有意推迟
- **非目标** — 明确在此工作之外

优先选择能够传递预期结果的最小连贯核心。

每个主要新增内容都应由产品需求证明其合理性。

### 6. 不猜测未解决的决策

区分：

- 可从证据回答的事实
- 由用户拥有的产品决策
- 由 RFC 拥有的技术问题
- 有意推迟的工作

如果产品意图仍然模糊，则询问。

如果未解决的问题是技术性的且不阻塞产品定义，则推迟到 RFC。

在此技能激活期间不要编辑产品代码。

## 流程

### 第 1 步 — 捕获方向

使用已确立的内容创建或更新 `prd.md`：

- 愿景
- 问题或机会
- 用户或受益者
- 期望结果
- 已知范围
- 已知约束

不要通过编造来填补空白。

### 第 2 步 — 检查证据

探索相关项目证据以确立：

- 当前行为
- 现有能力
- 先前决策
- 领域术语
- 相关约束
- 受影响的系统边界

将产品相关发现记录在 `prd.md` 中。

对于复杂工作，将实质性技术上下文保留在 `design.md` 中。

### 第 3 步 — 解决产品决策

识别对以下方面有实质影响的未解决决策：

- 结果
- 行为
- 范围
- 用户体验
- 兼容性
- 优先级
- 风险
- 成功

如果仍有一个或多个未解决，则问单个最高价值问题并停止。

在每次回答后：

1. 更新产物
2. 检查新相关的证据
3. 重新计算未解决决策
4. 必要时重复

不要进入实现或 RFC 设计。

### 第 4 步 — 塑形产品

完善：

- 核心范围
- 辅助范围
- 推迟工作
- 非目标
- 产品约束
- 预期产品行为
- 产品级成功

移除预期价值不要求的复杂性。

### 第 5 步 — 在需要时捕获设计上下文

对于复杂工作，创建或更新 `design.md`。

使用它来保留：

- 相关的当前系统事实
- 受影响的系统边界
- 既定技术约束
- 其他地方已确立的现有权威技术决策
- 兼容性或迁移影响
- 供 RFC 解决的技术问题

不要在 `design.md` 中做出新的技术决策。

`design.md` 是支持性上下文。RFC 拥有技术设计。

简单或局部的工作可以省略 `design.md`。

### 第 6 步 — 运行收敛门

仅当满足以下条件时，PRD 才准备好进行最终审查：

- 问题和期望结果清晰
- 用户或受益者清晰
- 产品价值已理解
- 预期产品行为足够清晰
- 核心范围有边界
- 有意义的非目标明确
- 重要产品约束已知
- 产品级成功已定义
- 不存在阻塞性产品决策
- 剩余技术问题可以移至 RFC，而无需 RFC 猜测产品意图

技术架构不需要解决。

### 第 7 步 — 收敛产物

在最终审查之前，将产物重写为最终形式。

移除：

- 已解决的问题
- 重复事实
- 已放弃的想法
- 探索性推理

保留：

- 决策
- 范围
- 约束
- 相关证据
- 重要假设
- RFC 交接问题

产物应描述已收敛的方向，而非对话历史。

### 第 8 步 — 最终审查

提供简洁的摘要，包含：

- 愿景和问题
- 期望结果和价值
- 核心范围
- 相关时的辅助或推迟范围
- 非目标
- 重要约束
- 产品级成功
- 重要设计上下文
- 推迟到 RFC 的技术问题
- 产物状态

然后停止。

不要在同一个回合中开始 RFC 设计或实现。

在 PRD 获得批准之前，需要用户明确批准最新的最终审查。

如果之后产品方向发生重大变更，则重复最终审查。

## PRD 模板

在可用时使用项目现有的 PRD 格式。

否则使用：

# PRD：<标题>

## 状态

草稿 | 提议 | 已批准

## 愿景

此产品或功能应实现什么？

## 问题

我们在解决什么问题或机会，以及为何重要？

## 用户

谁受益或受影响？

仅包含与实际产品决策相关的群体。

## 期望结果

当此成功时，什么应变得可能？

## 产品行为

描述重要的用户可见或外部可观察行为。

关注结果而非实现机制。

## 范围

### 核心

传递预期价值所需的能力。

### 辅助

有用但非核心所必需的相关能力。

### 推迟

有意推迟的能力。

## 非目标

明确在此工作之外的相邻问题或能力。

## 约束

影响产品行为的既定产品、平台、兼容性、业务、政策或运维约束。

## 成功

表明预期价值已实现的可观察产品级结果。

当不需要指标时，不要制造指标。

## 风险与假设

仅包含影响范围、价值或预期行为的重要产品假设或风险。

## 参考文献

相关研究、问题、PRD、RFC、ADR、规范、原型或代码库证据。

## 设计上下文

仅适用于复杂工作，创建或更新 `design.md`。

在可用时使用项目现有格式。

否则使用：

# 设计上下文：<标题>

## 当前系统

产品规划期间发现的相关当前系统事实。

## 系统影响

可能受影响的重大边界、能力或子系统。

## 约束

RFC 必须尊重的既定技术、兼容性、运维或迁移约束。

## 现有决策

其他地方已确立的相关权威技术决策。

不要在此处创建新决策。

## 供 RFC 解决的问题

有意推迟到下游设计的技术问题。

它们应可在不重新打开已批准产品意图的情况下回答。

## 参考文献

相关代码、测试、文档、RFC、ADR、规范、原型或研究。

## 产物状态

在发现期间：

- `prd.md` → `草稿`
- `design.md` → 需要时的支持性工作上下文

在收敛后：

- `prd.md` → `提议`

在最新最终审查获得明确批准后：

- `prd.md` → `已批准`

`design.md` 保持为支持性上下文，而非独立批准的设计契约。

## 交接

当满足以下条件时，已批准的 PRD 即可用于 RFC：

- RFC 不需要猜测产品意图
- 产品范围有充分边界
- 预期产品行为足够清晰
- 重要产品约束明确
- 产品级成功已理解
- 相关系统上下文已被保留
- 未解决的技术问题已被清晰识别

下游 RFC 工作使用：

- `prd.md` 作为权威产品方向
- `design.md`（存在时）作为支持性技术上下文

RFC 可以挑战 `design.md` 中的技术假设，但不得默默重新定义已批准的产品意图。

PRD 定义**是什么和为什么**。

设计上下文保留**规划期间了解到的关于系统的信息**。

RFC 决定**如何做**。
