# 编写 RFC

在实现之前产出设计 RFC。

RFC 回答：

> 应如何设计和实现此变更，以及为什么？

它不是 PRD、规范、任务列表或实现。

典型流程：

请求 → RFC → 批准 → 规范 → 任务 → 实现

## 规则

### 1. 不要实现

在最新 RFC 获得明确批准之前，保持在设计模式。

在 RFC 工作期间不要编辑产品代码。

之前的“实现”、“继续”或“继续推进”并不代表对后续 RFC 修订版本的批准。

### 2. 先检查，再询问

如果代码库能回答某个问题，就检查它，而不是询问用户。

检查相关：

- 代码和测试
- 配置
- 文档
- 规范
- ADR
- 相关 RFC
- 原型
- 问题/任务历史记录

代码库证据确立当前行为和约束，但不确立未解决的产品意图。

### 3. 仅询问真正的决策

仅在涉及以下内容时询问用户：

- 产品行为
- 范围
- 用户体验
- 兼容性
- 安全/风险
- 迁移
- 运维预期
- 有意权衡

不要问流程性问题。

### 4. 一次只问一个问题

如果仍有用户决策待定，则恰好问一个最高价值的问题。

每个问题必须包含：

- 该决策
- 为何重要
- 你的建议
- 主要权衡

在实现细节之前先解决上游决策。

### 5. 优先最小充分设计

每个有意义的机制都必须由需求、约束、兼容性需求、安全需求、运维需求或已证明的技术必要性来证明其合理性。

如果移除某物不会破坏任何重要内容，则移除它。

避免推测性可扩展性。

## 流程

### 第 1 步 — 定义问题

在不预设解决方案的情况下重述问题。

优先：

> 该操作可能比发起请求存活更久。

而非：

> 我们需要一个后台队列。

确定：

- 当前行为
- 期望结果
- 受影响的用户/系统
- 为何当前行为不足

### 第 2 步 — 检查当前系统

理解相关的：

- 架构和边界
- 数据/控制流
- 契约
- 状态归属
- 失败行为
- 生命周期/并发
- 兼容性约束
- 测试接缝

使用现有项目术语。

当设计实质性地引入或变更领域概念、所有权、不变量、关系或边界时，使用 `domain-modeling`。

### 第 3 步 — 构建决策清单

将未解决的问题分类为：

- **代码库** — 从代码库中回答
- **研究** — 从权威技术证据中回答
- **用户** — 需要意图、范围、用户体验、兼容性或风险选择
- **实验** — 需要基准测试、原型或概念验证

不要将未知项转化为假设。

### 第 4 步 — 评估备选方案

仅考虑有意义的备选方案。

对每个有用的备选方案记录：

- 方法
- 优点
- 成本
- 为何选择或拒绝

不要为了填充 RFC 而编造备选方案。

### 第 5 步 — 解决技术未知项

如果某个技术假设对设计有实质性影响且无法自信回答，则定义所需的最小验证。

示例：

- 针对性研究
- 基准测试
- 兼容性测试
- 原型
- 概念验证

阻塞性未知项必须在接受之前解决。

### 第 6 步 — 收敛

当满足以下条件时，RFC 即可进行最终审查：

- 问题清晰
- 目标/非目标清晰
- 代码库证据已被检查
- 所需用户决策已解决
- 主要边界清晰
- 重要流程/契约清晰
- 失败行为已理解
- 在相关时，兼容性/迁移已处理
- 有意义的备选方案已被考虑
- 权衡和风险明确
- 阻塞性技术未知项已解决
- 没有阻塞性的未决问题

如果仍有用户决策待定，则提出一个问题，而不是提交最终 RFC。

## 第一性原理检查

当设计显得复杂时，问：

1. 实际问题是什么？
2. 哪些事实是绝对确定的？
3. 哪些部分是假设或惯例？
4. 每个主要机制对应哪个需求？
5. 如果移除该机制，什么会被破坏？
6. 满足所有已知约束的最小设计是什么？

## RFC 模板

如果代码库有 RFC 格式，则使用该格式。否则：

# RFC：<标题>

## 状态

草稿 | 提议 | 已接受 | 已拒绝 | 已取代

## 摘要

问题、提议的设计以及为何优先选择它。

## 动机

当前限制及其重要性。

## 目标

- ...

## 非目标

- ...

## 当前状态

相关的现有行为和架构。

## 约束

相关的产品、架构、兼容性、安全、平台或运维约束。

## 提议设计

描述推荐的设计。

仅涵盖相关主题，例如：

- 架构和责任边界
- 数据/控制流
- 接口和契约
- 状态/生命周期
- 失败处理
- 并发
- 安全
- 兼容性/迁移
- 运维

## 考虑的备选方案

有意义的备选方案及拒绝原因。

## 决策理由

为何此设计最能满足目标和约束。

## 权衡

有意接受的重要成本。

## 风险

有意义的风险及缓解措施。

## 验证

支持重要假设的证据、研究、基准测试、原型或概念验证结果。

## 延期工作

明确推迟且不阻塞此设计的工作。

## 未决问题

仅包含未解决的问题。若无，则省略。

## 参考文献

相关的 PRD、ADR、RFC、规范、问题、原型、代码库证据或权威技术来源。

## 最终审查

当设计已收敛：

1. 将状态设置为 `Proposed`。
2. 提供简洁摘要，包含：
   - 问题
   - 目标/非目标
   - 提议设计
   - 关键决策
   - 被拒绝的备选方案
   - 权衡
   - 风险
   - 验证/延期工作
3. 停止。
4. 等待用户明确批准。

获得明确批准后，将状态设置为 `Accepted`。

重大的设计变更需要再次进行最终审查。

## 编写规则

- 解释为什么，而不仅仅是什么。
- 区分事实、约束、决策和假设。
- 优先使用稳定的设计概念，而非私有实现细节。
- 不要编写对话记录。
- 从最终 RFC 中移除已解决的问题。
- 不要制造复杂性、备选方案或问题。
- 在生成的 RFC 中使用项目术语。
- 保持可复用示例的领域中立。

RFC 是设计契约。下游规范将已接受的设计转化为实现和验收需求。
